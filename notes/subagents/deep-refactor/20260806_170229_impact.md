**리스크 레벨: medium** — C# `partial class` 분할 자체는 타입 동일성이 보존되므로 접근성·바인딩·리플렉션이 깨지지 않고, 실패 대부분이 **컴파일 타임에 즉시 드러남**. 단 아래 두 시나리오는 컴파일을 통과하며 런타임/테스트로 새는 경로.

**고장 시나리오 1 — using 별칭 누락으로 인한 타입 무성(無聲) 치환 (영향도: high)**
`MiniCapture.csproj`가 `UseWPF=true`와 **`UseWindowsForms=true`를 동시에** 켜고 `ImplicitUsings=enable` 상태. 원본 파일은 이 충돌을 13개 별칭(`WpfPoint`/`WpfRect`/`WpfColor`/`WpfRectangle`/`WpfShape`/`WpfPen`/`WpfBrushes`/`WpfClipboard`/`WpfCursors`/`WpfEllipse`/`WpfPath`/`WpfFlowDirection`/`WpfBinding`) + 본문 전체 완전수식으로 회피. 별칭은 **파일 스코프**라 새 partial 파일마다 재선언 필요, `Point`/`Rectangle`/`Color`/`Brush`는 `System.Drawing`·`System.Windows.Forms`에도 동명 타입이 있어 별칭을 빠뜨리면 컴파일 에러가 아니라 **다른 타입으로 조용히 해석**될 수 있음. 영향: 좌표 변환(R20)·픽셀 효과(R19) 전 경로. 테스트 커버리지가 그 지대에 낮아 검출은 수동 실행 뿐.

**고장 시나리오 2 — internal static 헬퍼의 소속 이탈로 테스트 동시 붕괴 (영향도: high)**
`SortFiles`·`CompareFiles`·`IsSameFolderSelection`·`RequiresDetailsView`·`CalculateCropRectangle`·`DecodeImageFile`·`ApplyGaussianBlurRegion`·`BuildGaussianKernel`·`MaxIconViewFiles`는 `tests/MiniCapture.Tests/Program.cs`가 **`ViewerWindow.` 접두로 정적 호출**. 이 멤버들이 partial 조각 안에 머무르면 무해하지만, ① 새 partial 파일의 선언이 `internal partial class ViewerWindow`로 달라지면 CS0262, ② "순수 함수니까"라는 이유로 별도 타입으로 이동하면 테스트 전부 즉시 깨짐. 이 멤버들이 리포지토리 전체에서 ViewerWindow에 대한 **유일한 자동 검증 지점**이라, 여기가 끊기면 4013줄 전체가 무검증 상태로 재배치됨.

**고장 시나리오 3 — 데드 코드 오판 (영향도: medium)**
`ApplyShape`/`ApplyText`/`ApplyPen`/`ApplyArrow`(약 120줄)는 참조 0인 사문화 코드. 분할 중 이들이 "래스터 적용" 파일로 옮겨가면 살아있는 `ApplyMosaic`(유일 생존)과 나란히 놓여 **현재 아키텍처가 아직 즉시-래스터 방식인 것처럼 오독**되고, 반대로 일괄 삭제하면 대체 경로가 사라질 수 있음. 어느 쪽이든 Phase 2에서 **명시적 결정 항목**으로 올려야 하며 분할 작업에 끼워 처리하면 안 됨.

# Phase 2(deep-reasoner)로 넘기는 제약 사실 (설계 아님)

1. XAML 바인딩 핸들러 47개와 `x:Name` 필드 61개는 `partial class ViewerWindow`의 멤버여야 함 — partial 유지 시 자동 충족, 별도 타입 추출 시 불충족.
2. csproj는 글로빙이므로 파일 추가 시 프로젝트 파일 수정 불필요.
3. 필드 53개 중 초기화자 간 상호 참조는 없음(검증 완료) → 필드 선언 분산 시 초기화 순서 문제는 현재 없음.
4. 재진입 가드 플래그 6종(`_isLoadingSelection` 등)이 영역 경계를 가로지르며, 특히 `_isLoadingSelection`은 R4·R6·R7·R8·R9 다섯 영역을 묶음.
5. `_editableImage`(43 메서드)·`_zoom`(14)·`_editTool`(10)이 상태 결합의 3대 축.
6. 검증 수단은 `dotnet build` + `dotnet run --project tests/MiniCapture.Tests` + **수동 UI 회귀**뿐. 자동 검증이 닿지 않는 대부분의 줄에 대해서는 "빌드 통과 = 안전"이 성립하지 않음.
7. 최근 변경 집중 영역(R10/R11/R12/R16/R18/R19)과 무변경 안정 영역(R3/R5/R13/R17/R20/R23)이 명확히 갈림.

# 메인에 대한 권고

**설계 검토 필요** — 분할 자체는 partial class라 기계적으로 안전하지만, 자동 검증이 극히 일부에만 닿고 `_editableImage`/`_zoom`/`_editTool` + 재진입 가드 6종이 영역 경계를 관통하므로, Phase 2에서 (i) internal static 헬퍼 전부의 소속 보존, (ii) using 별칭 세트의 파일별 복제 규칙, (iii) 데드 코드 4개 처리 방침을 먼저 확정해야 한다.
