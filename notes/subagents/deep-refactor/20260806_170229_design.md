## 4. using 별칭 배분 규칙

**규칙 U1 (필수)**: 새 조각 파일은 원본 `ViewerWindow.xaml.cs` 1–29행(네임스페이스 using 13 + 별칭 14[`IOPath` 포함] + `namespace MiniCapture;`)을 **한 글자도 바꾸지 않고 그대로 복사**한다. 파일별 취사선택 금지.
- 근거: 이름 해석 환경이 원본과 **증명적으로 동일**해진다(§0 F3의 논증에 의존하지 않는 무조건 안전). 파일마다 "이 별칭 필요한가?" 판단을 없애 기계적 이동의 성격을 유지한다. 미사용 using/별칭은 컴파일 에러도 경고도 아니다(csproj에 `TreatWarningsAsErrors` 없음).
- 비용: 12파일 × 31줄 ≈ 370줄 중복. 4000줄 파일을 나누는 대가로 수용 가능(정량).

**규칙 U2 (금지)**: IDE의 "using 정리 / Remove Unused Usings"를 이 파일들에 실행하지 말 것.
- 네임스페이스 `using` 제거는 이동한 코드에는 안전하지만(F3), **앞으로 그 파일에 코드를 추가할 때** `Point`/`Color`/`Brush`/`Rectangle`이 `System.Drawing`·`System.Windows.Forms`(implicit global) 쪽으로 해석되는 함정을 다시 연다. 별칭 세트가 곧 이 파일들의 안전장치다.

**규칙 U3 (선택, 전 단계 완료 후 별도 commit)**: 별칭만은 정리해도 안전하다 — 별칭은 코드에 이름이 명시적으로 등장하므로 잘못 지우면 CS0246으로 즉시 드러난다. 네임스페이스 `using`은 절대 정리하지 않는다.
- 이 규칙을 쓰면 §0 F4의 프로젝트 관례(`MainWindow.xaml.cs` = 쓰는 것만 선언)와도 정합. **단 이번 범위에서는 실행하지 않기를 권장** — 순수 이동 commit들과 섞이면 리뷰가 "이동인가 편집인가"를 구분하기 어려워진다. confidence: high.

**대안(기각) — "그 파일이 쓰는 별칭만 선언"**: 관례 정합·중복 370줄 절감이 이점이지만, 단계마다 13개 별칭 각각에 대한 판단이 들어가면서 diff가 "이동 + 편집"으로 오염되고 기계적 동등성 검증(§6)이 무력해진다. 트레이드오프상 이동 중에는 U1, 정리는 U3로 분리하는 편이 낫다.

## 5. 필드(53개) 배치 방침

**결정: const 10개 · 중첩 타입 2개 · enum 4개 · 인스턴스 필드 53개 전부를 앵커 `ViewerWindow.xaml.cs`에 잔류시킨다.** confidence: high

근거(5-why식 인과):
1. 왜 분산하지 않나 → 필드 20개 이상이 3개 이상 영역에서 읽고 쓰인다(Phase1 (b)). `_editableImage`는 43개 메서드·12개 영역, `_zoom`은 8개 영역.
2. 왜 그게 문제인가 → 소유 파일을 정하려면 "주 사용자"를 자의적으로 판정해야 하고, 그 판정은 **이번 작업의 목표(기계적 이동)에 없는 설계 결정**이다.
3. 왜 자의적 판정이 위험한가 → 판정 근거가 기록되지 않으면 다음 사람이 다시 옮기고, 필드가 파일 사이를 왕복한다(구조 illusion).
4. 왜 잔류가 검증에 유리한가 → `git diff`에서 **"102–155행 필드 블록 무변경"**이 단계마다 성립해야 하는 불변조건이 되어, 리뷰어가 한눈에 "필드는 안 건드렸다"를 확인할 수 있다.
5. 왜 지금 상태 결합을 풀지 않나 → 그것(=`ViewerEditSession` 추출 등)은 동작을 바꿀 수 있는 설계 변경이며 §7 범위 밖.

부수 이점: Phase1이 확인한 "초기화자 간 상호 참조 없음"에 계속 의존하지 않아도 된다(분산 시 향후 초기화자 추가로 잠복 위험이 생기지만, 한 파일이면 선언 순서가 곧 초기화 순서로 눈에 보인다).

기각한 대안:
- **F2 파일별 분산**: 조각 파일의 자기완결성은 오르지만 공유 필드 20+개에서 무너진다. 누락/중복은 컴파일 에러라 *안전하긴* 하나, 단계마다 판단이 들어가 diff가 오염된다.
- **F3 하이브리드(단일 영역 전용 필드만 이동)**: 대상이 10~15개뿐이라 이득이 작고, "전용인가"를 매 필드 확인하는 비용이 이득을 넘는다.

**허용되는 유일한 비-이동 추가(선택)**: 각 조각 파일 최상단에 **최대 5줄** 주석으로 "이 파일이 다루는 책임 + 주로 읽고 쓰는 공유 필드"를 명시. 필드가 앵커에 모여 있어 조각 파일만 봐서는 상태 접점이 안 보이는 문제(F1 방침의 유일한 단점)를 문서로 메운다. 이 외의 주석·리네임·서식 변경은 금지.

## 7. 롤백 포인트

- **사전 조치(필수)**: 시작 전 `git branch backup/pre-viewer-split`(또는 tag). 이후 모든 단계가 이 지점으로 완전 복귀 가능.
- **안전 경계**: **S0~S8의 모든 커밋 경계가 안전 정지점**이다(각 단계가 행동 중립이므로). 중단 시 앱·테스트 모두 정상.
- **권장 롤백 방식**: 특정 단계로 `git reset --hard <단계 커밋>` (= 그 이후 단계 폐기).
- **주의**: *중간 단계만 골라 `git revert`* 하는 것은 앵커 파일의 컨텍스트가 이후 단계에서 크게 이동해 텍스트 충돌 가능성이 높다. confidence: medium. 되돌릴 일이 생기면 "그 단계 이후를 통째로 reset" 이 실질적으로 유일하게 매끄러운 경로.
- **자연스러운 중간 정지점**: **S4 종료 시점**(파일 탐색·툴바·뷰포트 계열 분리 완료, 앵커 ~2200줄, 위험도 low~medium 구간만 소화). 편집 계열(S5~S8)을 다른 세션으로 미루더라도 그 자체로 완결된 개선이다.
